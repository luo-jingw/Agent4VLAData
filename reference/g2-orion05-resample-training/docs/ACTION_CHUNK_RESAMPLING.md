# 重采样 action chunk：按曲率代理选稀疏点

遥操数据按固定帧率录制，动作标签因此在**时间**上等距。这里把标签内部的动作序列改成
**一组按曲率代理挑出的稀疏点**，让固定长度的 action chunk 覆盖更长、更有信息量的
一段轨迹。

点在时间上不等距，在轨迹长度上也不等距——两者都不是这个方法的目标，见 §2。

方案与机器人型号、任务、数据集无关。下文一律称"机器人"与"遥操数据"；实测数字来自
一批真实遥操采集，只用来说明量级。

---

## 1 问题

部署时有两个硬约束，它们相乘决定了策略每次查询能"看多远"：

- **推理有延迟。** 每查询一次要花掉可观的时间，所以不能想查就查。
- **一次查询只输出固定条数的动作**（chunk 长度 `H`）。`H` 由模型结构和推理开销
  决定，不是可以随便调大的量。

于是：

```
单位时间能覆盖的轨迹范围  ≈  H × (每个动作点代表的轨迹长度)  /  查询周期
```

`H` 和查询周期都被推理成本按住了，**唯一还能动的是"每个点代表多长的轨迹"**。而这由
训练标签怎么排布决定：策略被训练成输出这种排布的 chunk。

**按时间均匀采样把这个量花在了错误的地方。** 遥操数据是按固定帧率录的，于是标签在
操作员犹豫、停顿、对位的地方最密，在机器人快速移动的地方最疏——正好和"哪里需要
密集监督"相反。实测一批遥操数据：

约 **19%** 的帧位移低于 `0.002 rad/帧`，它们只承载了 **0.23%** 的关节空间距离，
却占用了 **19%** 的监督预算。

也就是说，`H` 个点里有相当一部分花在了几乎没有前进的帧上，**每次查询覆盖的轨迹范围
被停顿吃掉**。要覆盖同样长的一段轨迹就得更频繁地查询，而查询频率被推理延迟卡死。

---

## 2 原理

**不是按轨迹长度均匀取点。** 等弧长在实测里是最差的规则(§5.1)。

方法是:**用曲率代理挑出一组稀疏点，代理的形式由"等化插值重建误差"决定，指数由实测选出。**

形式取自节点放置的经典结果——用分段多项式从 `N` 个点重建一条曲线时，最优节点密度是
二阶导数的某个分数次幂。**决定重建误差的是曲率而不是距离**：直线段走得再远也不需要点，
拐弯处走得再近也需要点。

具体指数没有从公式里推，是在这批数据上测出来的:

| 重建方式 | \|q″\|^(1/2) | \|q″\|^(1/3) | \|q″\|^(1/4) |
|---|---|---|---|
| 线性 | 18.29 | **13.60** | 15.19 |
| PCHIP | 11.81 | **10.41** | 10.91 |

线性与 PCHIP 两种重建方式下都是 `1/3` 最低，**换插值方式不改变这个选择**。

**实现手段**是把逐帧的密度累加成一个单调量 `s(t)`，再以固定步长在 `s` 上取 `H` 个点——
在 `s` 上等距，等价于让点距按密度的倒数变化。`s` 只是记账用的累加量，不代表任务进度，
被选择的是**点在轨迹上的稀疏分布**。

逐帧增量分两种区域:

```
ds(t) = ┌ step × min(event_points, 窗长) / 窗长     t 落在夹持事件窗口内
        └ |q″(t)|^(1/3)                            其余位置
```

**观测帧一帧不删。** 全部保留，每帧各自携带一个标签，**只有标签内部的动作序列是重采样的**。
这不是对数据集做抽稀。

## 3 算法

### 3.1 自由段：按曲率密度排点

对自由段（非事件），取 `ds = raw`，然后用**闭式解**求出统一步长。设：

- `T` 为帧数，`F` 为落在事件窗口内的帧数
- `A` 为事件窗口之外累积的 `s` 增量之和
- `frames_per_step = span_frames / H`，即"希望一个 chunk 往前够到多少帧"除以 chunk 长度

则

```
step = A × frames_per_step / (T − 1 − F)
```

`span_frames` 是这个设计真正要表达的量——**一个 chunk 应该往前够到多远**。点密度是
从它推导出来的，不是单独配的参数。早期版本直接暴露密度，名字还是从"执行速度"沿用
下来的，结果说的是实现细节而不是意图。

### 3.2 事件段：按时间排点

夹持事件（末端执行器开合命令的上升/下降沿，加上其后的物理过渡过程）**必须按录制时间
排点**，不能按曲率。两个独立的理由，任何基于弧长的规则都会死在上面：

**一、过渡过程是物理时长。** 它由物理决定而不由轨迹决定，不会因为轨迹播放得快就变快。
时长本身逐事件实测，各事件之间差别很大——同一批数据里抓取的中位数是 22 帧，
释放只有 1 帧。这段窗口承载的关节空间距离远少于它占用的时间，等弧长采样会把它**压缩**。
保留窗口是为了防这个压缩;"压缩之后策略会在过渡完成前就动"是设计时的担心，没有实测。

**二、对位段没有弧长可采。** 操作员把末端对准目标后会**停住**再触发。静止段在任何
弧长规则下、任何尺度下都拿不到采样点，于是"已经对好位，现在该触发了"这个状态永远
不会作为标签出现。时间是唯一能表达它的坐标。

事件窗口的定位是**逐事件实测**的：从命令沿开始，找反馈通道第一次越过阈值的帧。
不设固定下限——过渡时长是每批采集自己的属性，写死一个值就是它出错的方式。

每个事件窗口分到固定预算 `event_points`，**在时间上均匀铺开**，且不超过该窗口的帧数
（否则一帧两个点，产生重复标签）。

### 3.3 反解与插值

`s(t)` 在被死区归零的停顿处有平台，不可逆。加一个可忽略的漂移使其严格单调，落在
平台内的目标就会解到停顿内部某处，而由于平台几乎不跨越 `s`，取点会直接跨过去——
这正是想要的。

反解得到**分数帧号**后取值：

- **连续维**走 PCHIP（保形三次插值）：过每一个录制点，且不会像普通三次样条那样
  过冲出机器人从未做过的振荡。
- **二值维**（开合命令）取最近帧并重新二值化：阀门只有 0 和 1。

### 3.4 每帧一个 chunk，锚在自己身上

取点有两种做法，**出数据集用的是第一种**：

| | 曲率密度算在哪 | 一个 chunk 的起点 | 覆盖的源帧数 |
|---|---|---|---|
| **全局曲线 + 锚定起点**（在用） | 整条 episode 算一次 | 该观测自己的 `s` | 浮动 |
| 逐窗口重算（只在实验里） | 每个观测各自的窗口 `[t, t+span]` 内单独算 | 该观测 | 固定等于 `span` |

出数据集的调用链是 `progress_curve(整条) → all_chunks`；逐窗口那套
（`by_curvature_of` 在窗内重算并归一化，使 `H` 个点正好铺满窗口）**只出现在测量脚本里，
没有进过数据集**。

曲率曲线**在裁掉静止前缀之前、对整条录制**计算。先裁再算会把同样的密度分给更少的自由帧，
从而改变 `step`——那等于顺手改了轨迹的时间参数化，而裁剪的本意只是别把同一帧喂一百遍。



关键细节：**chunk 的取点从这一帧自己的 `s` 出发，不是从步长的整数倍出发。**

```
targets = s[frame] + [1..H] × step
```

这样每一帧的 chunk 都锚定在机器人当前实际所处的位置，而不是一个固定网格。超出
episode 末尾的点钳到最后一帧。

### 3.5 事件步加权

事件窗口按时间排点只是**阻止它被压缩**，并不会让它比周围更密——所以它在损失里并没
有额外的分量。而任务成功与否恰恰发生在那 ~10% 的帧上。因此对**源帧落在事件窗口内**
的 chunk 步给一个损失权重乘子。

## 4 核心代码

```python
def progress_curve(states, actions, cfg):
    """构造 s(t) 与统一步长 step。"""
    q = actions[:, cfg.metric.dims].astype(np.float64)

    if cfg.metric.metric == "curvature":
        second = np.linalg.norm(np.diff(q, n=2, axis=0), axis=1)
        raw = np.power(np.concatenate([second[:1], second]) + 1e-12, 1.0 / 3.0)
    else:                                   # "arc"
        raw = np.linalg.norm(np.diff(q, axis=0), axis=1)
    n = len(raw)

    # 事件窗口：命令沿 + 反馈越阈，逐事件实测；再往前扩一段对位帧
    windows = dwell_windows(states, actions, cfg.progress.seal)
    approach = np.zeros(n, bool); dwell = np.zeros(n, bool)
    for w in windows:
        approach[max(w.onset - cfg.progress.approach_frames, 0): w.onset] = True
    for w in windows:                       # 后置：过渡窗口压过相邻的对位窗口
        dwell[w.onset: min(w.end, n)] = True
    approach &= ~dwell
    event = approach | dwell

    free = np.maximum(raw - cfg.progress.deadzone, 0.0)
    free[event] = 0.0                       # 事件段不参与自由段的密度累积

    # 闭式步长
    n_free, total_free = n - int(event.sum()), float(free.sum())
    step = total_free * cfg.frames_per_step / n_free

    # 事件段：固定预算，时间上均匀，且不超过一帧一个点
    ds = free.copy()
    for lo, hi in _runs(event):
        frames = max(hi - lo, 1)
        ds[lo:hi] = step * min(cfg.progress.event_points, frames) / frames

    return ProgressCurve(s=np.concatenate([[0.0], np.cumsum(ds)]), ds=ds,
                         step=float(step), ...)


def invert(curve, targets):
    """`s` 值 -> 分数帧号。加漂移使 s 严格单调，好跨过停顿平台。"""
    t = np.arange(len(curve.s), dtype=np.float64)
    strict = curve.s + np.arange(len(curve.s)) * (max(curve.total, 1.0) * 1e-12)
    return np.interp(targets, strict, t)


def sample_actions(actions, t):
    """在分数帧号上取值：连续维 PCHIP，二值维最近帧 + 重新二值化。"""
    continuous = [d for d in range(actions.shape[1]) if d not in BINARY_DIMS]
    grid = np.arange(len(actions), dtype=np.float64)
    curve = scipy.interpolate.PchipInterpolator(grid, actions[:, continuous], axis=0)

    out = np.zeros((len(t), actions.shape[1]))
    out[:, continuous] = curve(np.clip(t, 0.0, len(actions) - 1.0))
    nearest = np.clip(np.round(t).astype(int), 0, len(actions) - 1)
    out[:, BINARY_DIMS] = np.round(actions[nearest][:, BINARY_DIMS])
    return out


def all_chunks(actions, curve, horizon):
    """每一帧的 chunk，(T, H, D)。取点锚在各自的 `s` 上。"""
    targets = curve.s[:, None] + np.arange(1, horizon + 1)[None, :] * curve.step
    t = invert(curve, np.clip(targets.ravel(), 0.0, curve.total))
    return sample_actions(actions, t).reshape(len(actions), horizon, actions.shape[1])


def all_chunk_weights(curve, horizon, key_weight):
    """源帧落在事件窗口内的 chunk 步，给一个损失权重乘子。"""
    targets = curve.s[:, None] + np.arange(1, horizon + 1)[None, :] * curve.step
    t = invert(curve, np.clip(targets.ravel(), 0.0, curve.total))
    index = np.clip(np.rint(t).astype(int), 0, len(curve.ds) - 1)
    inside = (curve.approach_mask | curve.dwell_mask)[index].reshape(len(curve.s), horizon)
    return np.where(inside, key_weight, 1.0)
```

另有一步与重采样无关但同源的清理：**裁掉开头的静止前缀**（关节测量与命令**同时**
安静的那一段）。录制普遍在操作员开始之前就已开机，这段帧关节恒定、图像只差传感器
噪声，是同一个训练样本重复几百次。两条轨迹都要求安静——只看测量值会在"命令已发、
尚未动"的延迟上冲过第一条命令，而那一帧恰恰是前缀里唯一有信息的。

## 5 实测与取舍

### 5.1 放置规则的选择(PCHIP 重建，末端误差 mm)

给定 `N` 个点重建整条轨迹。标签本身用 PCHIP 构建，所以这是选放置规则时该看的口径。

| N | 等时 | 等弧长 | **关节曲率** | 贪心(下界参照) |
|---|---|---|---|---|
| 20 | 56.1 | 83.7 | **40.5** | 46.9 |
| 30 | 27.6 | 42.6 | **21.6** | 21.6 |
| 40 | 16.9 | 31.8 | **11.8** | 14.1 |
| 60 | 8.5 | 19.5 | **6.0** | 7.2 |
| 80 | 5.5 | 15.2 | **4.5** | 5.5 |
| 120 | 3.1 | 9.9 | **2.7** | 3.3 |

三个结论:

- **等弧长是最差的**，比等时还差 1.5–3.2 倍，比曲率差 **2.7 倍**(N=40: 31.8 vs 11.8)。
  表里只给了数字;一个说得通的解释是它把点集中在长距离移动上，而停顿与对位段拿不到点。
  无论解释对不对，**"改成按轨迹长度均匀取"不是一个可用的方案**这一条是测出来的。
- 曲率规则在 N≥40 处**优于贪心**。贪心(逐点插在当前最差处)本来是拿来当参照的，它需要
  预知整条轨迹、没有可学的闭式规则;它并不是最优解的下界，这张表里也确实没有守住。
- **噪声地板 1.97 mm**:原始轨迹自带遥操抖动，与轻度平滑版的差距 p95 就是这个数。
  低于它的差别读不出信息。

### 5.2 为什么在关节空间做

| | 同样的点数 | 同样的浮点数 |
|---|---|---|
| 结论 | 差 5–10%，可忽略 | 末端空间好 11 倍 |

**同样点数下换到末端空间没有收益——关节曲率已经是末端曲率的好代理。** 那 11 倍全部来自
维度压缩(关节每点 22 个数 vs 位置每点 3 个数)，而这个收益买不到:笛卡尔路径不是动作，
需要 IK;冗余自由度的零空间无法由位置表示决定;且缺姿态。**故定在关节空间。**

### 5.3 滑窗放置的实验，与它没有回答的问题

chunk 每帧重规划一次，所以放点规则还要看**一致性**:相邻两个 chunk 把同一段轨迹放在
不同位置，控制端跟随的计划就每帧变形一次。这个量叫**重规划抖动**。

实测(`H=50`，误差与抖动，mm):

| 跨度 | 逐窗口 误差 / 抖动 | 固定全局网格 误差 / 抖动 |
|---|---|---|
| 100 帧 | **1.67 / 1.78** | 8.39 / 9.52 |
| 200 帧 | **3.31 / 3.21** | 39.70 / 34.23 |
| 400 帧 | **7.38 / 7.03** | 37.32 / 18.60 |

**逐窗口在两个指标上都大幅胜出。**

但这个实验**不能直接用来证明在用的做法是对的**，因为它一次改了两件事:逐窗口相对
固定全局网格，既换了起点锚定方式，又在窗内重算并归一化了密度。而在用的做法(§3.4)
是**两者之间**——锚定起点取自逐窗口，密度与步长仍是全局的。表里没有这一档。

所以能说的只有:固定全局网格明显最差;逐窗口最好;在用的做法继承了逐窗口的锚定方式，
**它到底落在哪，这张表没测。**

在用的做法有一个直接后果:**chunk 覆盖的源帧数随位置浮动**——临近事件时点密，`H=50`
只覆盖约 88 帧;自由移动时覆盖 200 帧以上;中位 120 帧。这是"密度全局、起点锚定"的必然
结果，也可以读成自适应:临近关键动作看得细，自由移动看得远。集尾越界的点钳到最后一帧，
实测 21.7% 的标签步属于这种填充。

### 5.4 被试过并否决的做法

| 做法 | 结果 | 结论 |
|---|---|---|
| 死区(把低于阈值的位移归零) | 停顿帧承担的监督从 0.52% 变到 0.72%，加速比与事件占比都不变 | **默认关闭**。曲率度量本身已经饿死了停顿，死区在解决一个已被解决的问题，还多一个每批数据要标定的阈值 |
| 给过渡窗口设固定帧数下限 | 在一批数据上标定的下限，换一批就在 83% 的事件上生效，把典型过渡拉长 1.32 倍 | **不设下限**。过渡时长是每批采集自己的属性，逐事件实测才是该信的数 |
| 事件窗口一帧一个点 | 8 个点重建事件段已落到 2.0 mm，与 1.97 mm 的抖动底噪同量级;一帧一个点要花约 52 个 | **固定预算**，且不超过一帧一个点 |
| 不给事件加权，只靠密度 | 早期自由段 1.2 帧/点、事件段 1 帧/点，密度只差 1.2 倍时成立;现在自由段 4 帧/点，密度差拉到 3 倍以上 | **要加权**。按时间排点只是"不被压缩"，不构成 loss 上的强调 |

## 6 消费这批标签的一方必须知道的

**这些标签不是时间均匀的，也不是弧长均匀的。** 点间距在实测数据上跨越 15 倍。
用固定速率回放它们，等于命令了一个跟着点间距走的速度。

这不是缺陷，是这个方案的定义：点密度携带的是"这段轨迹需要多少监督"，不是"这段轨迹
该用多快走"。任何回放侧都必须自己决定时间参数化。

**点之间怎么连也要一致。** 标签用 PCHIP 构建;若消费端把相邻点用直线连，实测代价稳定在
**1.2–1.4 倍**(N=40 时 13.6 mm 对 10.4 mm)。这是选择，不是错误，但要知道它存在。

同理，**开环评测不能按序号逐点比对**：第 k 个标签点故意比录制的第 k 帧走得更远，
同序号相减会把这个有意的提前量算成误差，且 k 越大越严重。正确的比法是拿预测点去比
**录制轨迹本身**的最近点——那个量对标签怎么重采样免疫。

## 7 参数一览

| 参数 | 含义 | 备注 |
|---|---|---|
| `metric` | `curvature` / `arc` | **用 `curvature`**。`arc` 是早期规则，实测最差(§5.1)，保留只为可复现对比 |
| `span_frames` | 一个 chunk 应往前够到多少录制帧 | 设计意图直接表达的量 |
| `action_horizon` (`H`) | chunk 长度 | 由推理成本决定 |
| `frames_per_step` | `span_frames / H`，自由段密度 | **推导量，不单独配** |
